# LexDefense Pipeline Design

## Goal

Build a standalone Python MVP inside this repository that prepares an auditable first draft of a `contestacion de demanda` in Colombia for `reparacion directa` cases with optional `llamamiento en garantia`, while enforcing evidence-first drafting, deterministic validation, and mandatory human approval.

## Placement

The implementation will live in a dedicated subproject at `lexdefense-pipeline/` instead of being merged into the existing `backend/` consumer-rights pipeline.

Reasons:

- it avoids coupling two different legal workflows;
- it preserves the green baseline of the existing FastAPI app;
- it lets the MVP match the requested CLI and file layout closely;
- it remains easy to demo or extract later as its own repository.

## Product Shape

The MVP is not an autonomous lawyer.

- Every generated document is marked `BORRADOR PARA REVISION HUMANA`.
- No filing, signing, or deadline finalization is automated.
- Legal citations generated by the model remain `UNVERIFIED` unless they come from a locally loaded legal corpus and are matched deterministically.
- Export as `FINAL` is blocked when approvals are pending, citations remain unverified, or validators raise blocking issues.

## Architecture

The subproject uses a sequential pipeline with five layers.

1. `ingest`
- read PDF and DOCX files from a run input directory;
- extract text per page or document;
- assign basic document labels;
- persist page-level sources with stable identifiers.

2. `case build`
- assemble a `CaseSchema` from extracted pages;
- infer parties, tribunal, radicado, dates, policy references, and procedural context using deterministic parsing first and LLM-assisted extraction second;
- store editable JSON before downstream drafting.

3. `facts and evidence`
- extract numbered facts from the complaint;
- split each fact into `AtomicClaim` items;
- classify each claim from the represented party's role;
- build the evidence matrix with support, contradiction, gaps, proposed response, risk, and human question.

4. `draft`
- create paragraph-level draft objects with traceability metadata;
- render Markdown and optional DOCX outputs;
- use uncertainty markers when support is missing.

5. `audit and export`
- run adversarial audit and deterministic validators;
- generate human checklist and export status;
- allow only `BORRADOR AUDITADO` when blocking issues remain.

## Runtime Strategy

The system must work without external APIs.

- `LLMClient` supports `mock` mode by default.
- If `OPENAI_API_KEY` exists, the same interfaces can call a real model.
- All core validators, exporters, and run orchestration remain deterministic and testable without network access.

## Project Layout

The new subproject will follow this layout:

- `lexdefense-pipeline/README.md`
- `lexdefense-pipeline/requirements.txt`
- `lexdefense-pipeline/.env.example`
- `lexdefense-pipeline/app.py`
- `lexdefense-pipeline/src/lexdefense/...`
- `lexdefense-pipeline/tests/...`

Inside `src/lexdefense/`, the code is split by responsibility:

- `config.py`, `models.py`, `llm_client.py`
- `extractors/` for PDF, DOCX, and page classification
- `retrieval/` for chunking, corpus loading, and simple retrieval
- `pipeline/` for orchestration, fact extraction, evidence matrix, drafting, and audit
- `validators/` for deterministic gates
- `exporters/` for Markdown, CSV, DOCX, checklist, and status files
- `prompts/` for internal prompt templates

## Legal Corpus Strategy

The MVP supports `expediente + corpus curado local`.

The application will load optional legal sources from `lexdefense-pipeline/data/legal_corpus/` using a simple manifest-driven format.

Expected first-pass corpus buckets:

- `constitution/`
- `statutes/`
- `case_law/`

Each source should have:

- the original text file, preferably `.md`, `.txt`, `.pdf`, or `.docx`;
- metadata with title, authority, date, jurisdiction, and source identifier.

The MVP will not scrape or fetch law automatically.

## Data Model

Core Pydantic models:

- `CaseSchema`
- `Party`
- `Counsel`
- `DocumentSource`
- `PageText`
- `AtomicClaim`
- `FactItem`
- `EvidenceItem`
- `DefenseTheory`
- `InsuranceProfile`
- `DraftParagraph`
- `DraftDocument`
- `ValidationIssue`
- `HumanApprovalState`
- `PipelineRun`
- `LegalCitation`

The critical design rule is that generated prose never becomes the system of record.

- `CaseSchema`, `FactItem`, `EvidenceItem`, `DraftParagraph`, and `ValidationIssue` are persisted as structured JSON.
- Markdown and DOCX are render targets derived from structured state.

## Error Handling

The pipeline fails closed.

- unreadable or unsupported files are recorded as issues instead of silently skipped;
- missing evidence downgrades output to review markers;
- invalid role-sensitive language becomes a validator issue;
- export status is computed from approvals, citation verification state, and issue severity.

## Testing

The MVP uses TDD and keeps the deterministic core well covered.

Minimum required tests:

- `CaseSchema` required-field validation;
- `FactItem` to `AtomicClaim` splitting behavior;
- `TemplateResidueValidator` detection;
- `TraceabilityValidator` source enforcement;
- `InsuranceGateValidator` no-automatic-coverage behavior;
- `ExportGateValidator` blocking behavior for critical issues and unverified citations.

## Future Coworker Hooks

The MVP will not claim to outperform lawyers, but it will preserve the hooks needed to evaluate that later.

- `confidence_score` on claims, evidence rows, and paragraphs;
- `evaluation_log.json` per run;
- structured issue taxonomy;
- explicit `escalation_reason` when the system cannot proceed safely.

These hooks make it possible to compare the assistant later against human reviewers on measurable dimensions such as unsupported-claim rate, residue rate, escalation precision, and citation-verification compliance.

## Inputs Still Needed From You

To unlock verified legal citations in the MVP, you should prepare a small local corpus with at least:

- `Constitucion Politica de Colombia`;
- `CPACA`;
- the relevant insurance provisions you want treated as authoritative;
- a curated set of Consejo de Estado decisions for `reparacion directa` and `llamamiento en garantia`.

The implementation can start without those files, but until they are loaded the system will correctly keep suggested citations as `UNVERIFIED`.
